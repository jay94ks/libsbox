# 2026-10-04 vpn 모듈: WireGuard와 오버레이 드라이버

- `modules/vpn`의 `wg/` 하위 영역만 추가함(`vpn.hpp`, `modules/vpn/CMakeLists.txt`는 고치지 않음 — IPsec/L2TP가
  같은 모듈에서 동시에 만들어지는 중). core와 net도 고치지 않음.
- 프로토콜은 I/O 없는 `CWgEngine`로 먼저 만들고 시계를 주입받게 해서, 메모리 안 두 엔진으로 타이머(120s
  재협상, 180s 만료, 90s 포기, keepalive)를 실제 시간을 기다리지 않고 검증함. 장치(`CWgDevice`)는 그 위에
  TUN/UDP/timerfd와 recvmmsg/sendmmsg 일괄 처리를 얹은 껍데기.
- 알려진 답: WireGuard 공식 벡터를 외워 쓰는 대신, 백서대로 짠 독립 Python 구현(hashlib BLAKE2s,
  `cryptography` 패키지, 직접 짠 HChaCha20)으로 고정 입력의 메시지/키/쿠키 응답을 만들어 C++ 출력과 바이트
  단위로 비교함. 첫 시도에 모두 일치.
- 커널 모듈이 없는 환경이라 커널 경로는 genl 메시지 인코딩/디코딩(분할, 다중 응답 병합)만 단위 테스트하고,
  실제 장치 테스트는 MESSAGE로 건너뜀. `EWGM_AUTO`가 사용자 공간으로 대체되는 것은 확인함.
- 사용자 공간 장치에 wireguard-go와 같은 UAPI 소켓을 붙여 공식 `wg` 도구와 `sbox-wg show`가 다른
  프로세스의 장치를 읽고 바꿀 수 있게 함. 오버레이 드라이버도 실행 중 피어 변경을 이 경로로 보냄.
- 오버레이는 VXLAN 같은 L2 확장 대신 호스트별 서브넷 + L3 라우팅으로 설계함: 브릿지가 호스트 서브넷의
  게이트웨이를 갖고, 다른 호스트 서브넷은 `dev wgo-* src <게이트웨이>` 경로로 보냄. 컨테이너에는 호스트
  서브넷만 on-link로 주고 오버레이 전체 대역은 게이트웨이 경유 경로로 줌(ARP가 호스트를 넘지 않음).
- 발견해서 고친 문제:
  - IPAM이 `ip-range`의 네트워크 주소(.0)를 첫 컨테이너에 줌(전체 서브넷의 네트워크 주소만 제외하므로):
    오버레이 요청은 범위를 `.1`~`브로드캐스트-1`로 지정하도록 `MakeWgOverlayNetwork`를 고침.
  - 같은 이름(`wg0`)의 두 사용자 공간 장치가 같은 UAPI 디렉터리를 쓰면 나중 것이 소켓을 가로챔: 테스트에서
    디렉터리를 나누고 제한 사항에 적음.
  - 범위 for 문에서 `CNlAttrs::nested(...).items()` 임시 객체 수명 문제(-Werror=dangling-reference): 변수로 받음.
  - TUN이 밖에서 삭제되면 읽기가 EBADFD로 계속 실패해 루프가 돌 수 있음: 장치를 닫고 `wait()`를 깨움.
  - kernel 테스트 도우미가 임시 `CNlAttrs`의 속성 포인터를 들고 있던 use-after-free(ASan으로 발견).
- ASan/UBSan 빌드에서 vpn_wg 테스트 8개 모두 통과. 전체 `ctest -j8` 30개 통과.
- 남은 일(제한 사항 참조): 피어 자동 발견 제어 평면, 오버레이 IPv6 서브넷, wg-quick의 DNS/기본 경로 정책
  라우팅, 사용자 공간 GSO/다중 스레드.
