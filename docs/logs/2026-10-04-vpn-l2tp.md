# 2026-10-04 vpn: L2TP/IPsec 서버

브랜치 `claude/sbox-vpn-l2tp`. 설계는 [../vpn-l2tp.md](../vpn-l2tp.md).

## 한 일

1. IKEv1 코덱과 키 유도(`ikev1.hpp`, `ikev1crypto.hpp`). 기댓값은 Python `hashlib`/`hmac`/`cryptography`로 따로 계산해
   테스트에 넣었고 처음부터 일치했습니다.
2. IKEv1 엔진 하나를 응답자/개시자 두 역할로 씀(`ikev1peer.hpp`). PSK Main Mode는 ID가 PSK로 만든 키로 암호화되어
   오므로 후보 PSK를 대입해 복호화하는 방식으로 키를 고릅니다. 콜백은 엔진 상태가 정리된 뒤 실행되도록 큐에 모읍니다
   (콜백 안에서 소유자가 엔진을 다시 부르거나 지울 수 있음).
3. L2TPv2 터널(LNS/LAC), PPP(서버/클라이언트) — 동기 상태 기계로 만들어 메모리 안에서 서로 붙여 시험.
   PPP 손실 테스트에서 "Ack를 잃은 Configure-Request 재전송"을 RFC대로 재협상으로 처리하면 링크가 계속 흔들려,
   같은 식별자·내용의 요청에는 Ack만 다시 보내도록 바꿨습니다. 재전송은 같은 식별자를 씁니다.
4. 데이터 경로: 이 머신에는 esp4가 없으므로 사용자 공간 ESP transport 모드(raw ESP + NAT-T 소켓)를 주 경로로 구현.
   NAT-T 소켓을 IKEv2 데이터 경로와 함께 쓰려고 `CIkeSocket::espSpiHandler`(SPI별 ESP 처리기)를 ipsec/에 추가했습니다
   (기존 동작 변화 없음). 커널 XFRM transport 경로는 코드만 있고 실행 검증은 못 함.
5. `CL2tpServer`(TUN 하나에 모든 세션, 풀 재사용, IKEv2와 포트 공유), `CL2tpClient`(종단 간 테스트와 호스트 접속용),
   `sbox-l2tp`(run/check/profile/nthash), 프로파일 생성(Windows/Apple/Android).
6. 종단 간 테스트: 세 netns(클라이언트, 서버, 서버 뒤 LAN)에서 실제로 UDP가 클라이언트 TUN → ESP → L2TP → PPP →
   서버 TUN → LAN 호스트까지 왕복합니다(raw ESP, NAT-T 강제, IKEv2와 포트 공유, IPsec 없는 L2TP).
7. 퍼징 테스트와 함께 ASan+UBSan 빌드(`-DSBOX_SANITIZER=address,undefined`)로 l2tp 테스트 전부를 돌려 오류가 없음을 확인.

## 결정

- MPPE/CCP는 Protocol-Reject: L2TP/IPsec에서 Windows의 "암호화 필요"는 IPsec을 뜻하고 MPPE를 요구하지 않습니다.
- IKEv1 RSA 서명 인증 제외: DigestInfo 없는 PKCS#1 서명을 libcertpp가 제공하지 않음. 같은 이유로 IKE 단편화도 제외.
- 터널 하나에 세션이 하나도 남지 않으면 StopCCN(Windows 동작과 맞춤).
- Android 12+는 새 L2TP/IPSec 프로파일을 만들 수 없음을 문서와 프로파일 안내에 명시하고 IKEv2를 권함.

## 남은 것

- 실제 OS 클라이언트, xl2tpd/pppd/strongSwan과의 상호 운용 시험(도구가 없어 interop 테스트는 건너뜀).
- 커널 XFRM transport 경로의 실행 검증, IPv6CP, IKEv1 인증서 인증.
