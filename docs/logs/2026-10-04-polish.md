## A. 부하 아래 테스트 안정성

### 방법

- 기준선: 수정 전 빌드로 `ctest -j16` 21번 연속(이 기계는 4코어) → 모두 통과. 이 기계에서는 그것만으로는
  재현되지 않았습니다.
- 더 센 부하: 바쁜 루프 4개를 띄운 채 `ctest -j16` 8번(실패 1번: `box_sandbox`의 cpu 시간 케이스),
  그리고 실행 파일마다 12~16개 사본을 동시에 2~4라운드 돌리는 스트레스(`stressall.sh`, 모든 80개 실행 파일).
- 실패마다 로그와 임시 디버그 출력으로 원인을 확인한 뒤 고치고, 같은 스트레스를 다시 돌려 0이 되는지 봤습니다.

### 찾은 흔들림과 원인

| 테스트 | 증상 | 근본 원인 | 수정 |
|---|---|---|---|
| `oci_runtime` "hooks run in order..." | `-j16`에서 줄 순서가 틀림(보고됨) | 런타임은 시작 게이트를 연 뒤, `start`가 돌아오기 전에 poststart 훅을 돌립니다(OCI 명세 그대로). 컨테이너 프로그램은 그와 동시에 돌므로 `program` 줄과 `poststart` 줄의 순서는 정해지지 않는데 테스트가 `program`이 먼저라고 가정 | 테스트가 훅끼리의 순서는 엄격히, `program` 줄은 startContainer와 poststop 사이(4번째나 5번째)인지만 확인(`modules/oci/tests/runtime.cpp`) |
| `box_sandbox` "cpu time limit ends with the cpu reason" | 부하에서 `cpuTimeUs` 815~899 ms < 900 ms(보고된 "rootless 출력만 보이던" 실패가 이것: rootless 케이스의 `MESSAGE`는 정상 출력) | 커널은 `RLIMIT_CPU`를 틱 단위로 샘플링한 user+system 시간으로 검사하고, 결과의 `cpuTimeUs`는 cgroup의 정확한 실행 시간. CPU를 다투면 틱 샘플링이 바쁜 태스크에 더 매겨져 SIGXCPU가 실제 0.82~0.90 s에 옴. 라이브러리 버그가 아니라 두 값의 출처 차이 | 테스트는 이유(`EBEXIT_CPU_TIME`)와 0.5~5 s 범위만 확인. `docs/box.md`에 차이를 적음 |
| `box_sandbox` "wall timeout kills the program and its descendants" | `tree.size() >= 4`가 1 | 400 ms 제한 안에서 고정 200 ms를 잔 뒤 셸이 자식을 다 만들었으리라 가정(경쟁) | 프로그램이 자식을 만든 뒤 `ready`를 출력하고, 테스트는 그것을 읽은 뒤 트리를 폴링. 제한 3 s(`modules/box/tests/sandbox.cpp`) |
| `oci_compat` "create failures are reported in the JSON log" | 사본 12개 중 절반 실패: `create`가 0으로 끝나거나 `mount source /sys/fs/cgroup/cpu/sbox/x1: No such file` | 고정 컨테이너 id `x1` → 기본 cgroup `sbox/x1`을 모든 상태 루트가 공유. 한 사본의 `delete --force`가 다른 사본의 init을 죽이고 cgroup을 지움. init이 죽으면 `findExecutable`이 `/proc/<pid>/root`를 못 열어(ENOENT) 검사를 건너뛰고 create가 성공을 보고(라이브러리 결함) | 테스트는 고유 id. `findExecutable`은 init이 사라졌으면 `-ESRCH`("container init exited during setup")로 create를 실패시킴(`modules/oci/src/runtime.cpp`) |
| (데몬 테스트 전반: `vol_daemons`, 새 `vpn_wg_plugin`) | 새 데몬 테스트의 첫 실행에서 플러그인 호출이 연결 실패 | `CListener::listen`이 `bind()`로 소켓 파일을 만든 뒤 `listen()`하므로 그 사이에 파일을 보고 접속한 클라이언트(dockerd 플러그인 발견, 감독 프로그램, 테스트의 `waitForSocket`)가 ECONNREFUSED를 받음. 기존 코드에서 회귀 테스트가 400번 중 1번 재현(새 데몬 테스트의 첫 실패도 이 창으로 보임: 데몬 쪽 처리는 정상이었고 다시 재현되지 않음) | UNIX 경로 소켓은 같은 디렉터리의 임시 이름에 bind + listen한 뒤 `rename`으로 제자리에 옮김(남은 소켓도 원자적으로 교체, 소켓이 아닌 파일은 `-EADDRINUSE`, `localEndpoint()`는 요청한 경로). 회귀 테스트 `core_socket`(`modules/core/src/socket.cpp`, `include/sbox/core/socket.hpp`) |

시간 제한을 늘린 곳은 wall-timeout 케이스(관찰 대상이 실제로 느려지므로)뿐이고, 나머지는 경쟁이나 측정
가정을 고쳤습니다.

## B. CLI 공백

1. `sbox-image bundle`에 `-v/--volume`, `--mount`, `--tmpfs`, `--volume-root`, `--network`, `-p/--publish`,
   `--netns`, `--net-state-dir`, `--netns-dir`. 연결은 도구(`cli/sbox-image/attach.cpp`)에서만 하고 image
   라이브러리는 vol/net에 의존하지 않습니다. 붙인 것은 `<store>/attachments/<id>.json`에 기록하고, 실패하면
   전부 되돌립니다. `sbox-image rm [-v]`가 연결 해제, netns 삭제, 볼륨 해제(익명 볼륨 삭제)를 합니다.
2. `sboxnet`이 vpn 모듈을 링크해 `CWgOverlayDriver`를 등록하고 시작할 때 `restore()`. `--host-netns`,
   `--wg-uapi-dir` 옵션. Docker 플러그인은 `sbox.driver`가 없어도 `sbox.wg.overlay(.file)`이 있으면
   `wg-overlay`를 고릅니다. Docker 없이 쓰도록 `sboxnet network create/ls/inspect/rm`도 더했습니다
   (`bundle --network`가 붙을 네트워크를 만드는 수단). 테스트 `vpn_wg_plugin`(핸들러 경로 + 데몬 재시작 복구).
3. e2e `e2e_bundle_attach`: 임시 호스트 netns에서 `sboxnet network create` → `sbox-image bundle -v ... --tmpfs
   ... --network ... --publish 0:8080/tcp` → `sbox run --detach` → 호스트 netns에서 컨테이너 주소와
   127.0.0.1의 게시 포트로 접속 → `rm -v` 뒤 아무것도 남지 않음, `--netns`, 잘못된 조합의 롤백.

문서: `usage.md`, `image.md`, `vol.md`(sboxnet), `vpn-wg.md`, `net.md`, `e2e.md`(낡은 README 제한 사항 정리),
`box.md`.

## 남은 것

- `bundle --network`는 컨테이너의 `/etc/resolv.conf`·`/etc/hosts`를 쓰지 않습니다.
- `sboxnet network create`로 만든 사용자 공간 `wg-overlay` 장치는 명령이 끝나면 내려가고 `sboxnet` 데몬이
  시작할 때 복구됩니다(커널 모듈이 있으면 그대로 남음).
